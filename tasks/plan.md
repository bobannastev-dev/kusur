# План: web-app

Spec: `SPEC-web-app.md` (одобрен 2026-10-02). Макета: https://claude.ai/artifact/AQCJhGzxbfJwoaqrHReiYi. Задачите: `tasks/todo.md`. Претходни модули: `tasks/price-ingest/`, `tasks/product-matching/`, `tasks/price-history/`.

## Преглед

Три фази: (1) пакет со цени за телефонот и логика што работи во прелистувач, (2) Next.js апликацијата со четирите екрани локално, (3) дневното објавување преку GitHub Actions на Vercel. Секоја фаза завршува со нешто што може да се провери: тест, апликација на телефон, вистинска објава.

## Архитектонски одлуки

- **Прво раздвојување, па UI.** `match.ts`, `basket.ts`, `history.ts` при вчитување ги читаат мапите од диск (`category-map.ts`, `product-map.ts` → `node:fs`). Пресметката од кандидати (`cheapestFromCandidates`, кошничка преку „извор на кандидати") се издвојува во модули без `node:fs`; постојните функции остануваат со ист потпис и однесување (постојните тестови не се менуваат).
- **Пакетот носи кандидати, не ценовници.** `build-data` повикува `findCandidates` за секој тип × продавница; телефонот никогаш не ги вчитува мапите ни целосните снимки.
- **Каталогот оди како код** (`catalog.ts` е чист, со RegExp правилата), не како `catalog.json` — отстапување од spec-от: помалку дуплирање, истите алијаси за `parseList`.
- **Next.js ги увезува постојните `src/*.ts`** (со `.ts` наставки, `allowImportingTsExtensions`); ако Next не ги прифати, тенок слој `app/lib/` што ги реекспортира — проверка во задача 3.
- **Состојба на телефонот** во еден мал модул (`app/lib/storage.ts`): кошничка, следени типови, последна посета; сè преку `localStorage` со try/catch.
- **Стил:** CSS променливите од макетата (светла/темна), глобален CSS + CSS модули по компонента.
- **Pipeline на крај**, кога апликацијата веќе работи локално; бара GitHub repo и Vercel сметка од корисникот.

## Граф на зависности

```
1 раздвојување на логиката ── 2 build-data ──┬── 3 Next.js основа (мени, тема, податоци)
                                              │      ├── 4 Кошничка
                                              │      ├── 5 Пребарај (+ историја, ѕвезда)
                                              │      ├── 6 Поевтинето
                                              │      └── 7 Продавници + инсталирање/офлајн
                                              └── 8 GitHub Actions + Vercel (по 3–7)
```

## Задачи

### Фаза 1: Податоци за телефонот
1. Логика без `node:fs` (кандидати → купување, кошничка, историја)
2. `npm run build-data` → `public/data/types.json`, `stores.json`

**Checkpoint A:** критериуми 1–2 од spec-от (тестови); големина на пакетот.

### Фаза 2: Апликацијата (локално)
3. Next.js основа: зависности, static export, фонтови, тема, мени долу, вчитување на пакетот, `localStorage`
4. Екран Кошничка
5. Екран Пребарај (историја на производ, „вистинска акција?", ѕвезда)
6. Екран Поевтинето
7. Екран Продавници; manifest и офлајн

**Checkpoint B:** критериуми 3–5 — на твојот телефон преку `npm run dev` (иста Wi‑Fi мрежа); преглед со тебе.

### Фаза 3: Секојдневно објавување
8. GitHub Actions (`daily.yml`): враќање на податоците, fetch, зачувување, build, deploy на Vercel

**Checkpoint C (модулот готов):** критериуми 6–7; прво вистинско дневно објавување; `/review`; Second Brain.

## Ризици

| Ризик | Влијание | Мерка |
|---|---|---|
| Next.js не ги прифаќа `.ts` увозите од `src/` | Средно | Проверка веднаш во задача 3; резерва: реекспорт преку `app/lib/` |
| Пакетот е преголем (историја × кандидати) | Средно | Мерење во задача 2; серии само за денови со промена; ако треба — само последните 90 дена во пакетот |
| Стакло (`backdrop-filter`) бавно на слаби телефони | Ниско | Помалку замаглување на долги листи; проверка на твојот телефон во Checkpoint B |
| Жито трае ~50 мин во Actions | Ниско | Рок на задачата 2 часа; неуспешна продавница не ја спречува објавата |
| Губење на податоците меѓу деновите (Release) | Високо | 7 дневни копии; workflow не објавува празно ако враќањето не успее |
| Токени | Високо | Само во GitHub Secrets, ги внесуваш ти |
